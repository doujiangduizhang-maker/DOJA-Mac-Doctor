# 诊断规则与准确性边界

扫描与规则模块只读取目录项和文件元数据，生成说明与建议，不处理文件。0.2 的独立执行模块仅在用户勾选并点击移至废纸篓后，处理通过全部核实的固定缓存叶目录；黄色与红色项仍不能处理，见 [清理安全说明](CLEANUP-SAFETY.md)。下列官网链接是开发时核对路径语义的资料。

## 大小与可回收空间

- `logicalBytes` 是已读取文件的逻辑大小；目录记录是其已扫描子树的统计。
- `allocatedBytes` 是扫描器取得的分配大小，用于观察磁盘占用线索，不等于 APFS 容器实际独占数据块，也不等于一定能释放的容量。
- `estimatedReclaimUpperBound` 只有完整扫描、非红色且没有已知多重硬链接的文件才提供。展示为 **0 至上限**，最低值始终为 0；红色、部分扫描、已知多重硬链接文件不提供估算。
- APFS 快照、克隆共享块、硬链接、运行中打开的文件会影响回收。目录之间即使路径不重叠，仍可能共享物理块；不能把建议的上限相加后当成承诺。
- 移入废纸篓不是释放容量。确认后的移动结果与系统可用容量分开显示，不自动清空废纸篓。
- 文件排名和目录排名来自扫描器；诊断列表只选择互不包含的路径，避免同时列出一个建议父目录与其建议子目录。
- 未完整扫描的目录显示已读取部分与未扫描说明，不能视为空目录，也不给回收估算。部分读取的绿色缓存线索降为黄色“缓存用途与覆盖待确认”；完全未读取文件的缺失/无权限根目录不生成缓存建议，保留在未扫描问题列表。零条发现表示规则没有命中，不表示电脑没有问题。

## 风险规则

| 级别 | 首版用途 | 主要限制 |
|---|---|---|
| 绿色 | 标准 `Library/Caches/{Codex,com.openai.codex}` 路径、Codex 应用数据中的 GPU / Code Cache 等明确缓存子目录 | 可再生成的路径线索；应用退出后仍需核对。发现受保护后代时取消整目录建议。 |
| 黄色 | Crashpad/pending、运行日志、开发依赖、构建缓存、影视缓存与临时工作副本 | 需要确认正在使用的工程、离线依赖、日志保留与用途。目录名不能证明每个内容都可删除。 |
| 红色 | 会话、工作树、用户配置、版本库、原始媒体、作品输出、工程、数据库与用途不明的 Codex 数据 | 默认保留；不提供可回收估算。 |

生成规则只查看扫描元数据，不打开工程、数据库、登录信息、会话内容或媒体内容。不使用文件内容推断用途。逐文件保护检查运行于**每一个实际遍历的普通文件**，并向所有父目录传播 `containsProtectedFiles`；不受最大文件与最近大型文件各 50 条的排名限制。目录匹配缓存/临时规则、但包含需要保留的文件时，转为红色“混有需保留文件”并取消回收估算。这样一个很小的代码、配置或素材文件也不会因未进入排名而被遗漏。

文件诊断卡片仍只覆盖最大文件与最近大型文件的元数据，目录卡片覆盖扫描器保留的目录记录。保护检查只根据名称与扩展名，不是文件内容审计。未来执行任何清理前必须重新核对待处理范围，不能将首版建议直接作为删除清单。

显式的受保护目录与文件规则优先于缓存或临时名称。候选缓存父目录若包含已识别的会话、工程、数据库、素材、输出或代码，则不能作为整目录建议。项目的 `node_modules` 是黄色，因可能含本地修改与离线包。`.build`、`.next`、`.turbo` 等只是构建线索，同样保持黄色；整个 `build`、`dist`、项目目录及工作树不会被标作可清理单位。

## Codex

官网故障排查资料列出应用日志 `~/Library/Logs/com.openai.codex`，会话位于 `$CODEX_HOME/sessions`，归档会话位于 `$CODEX_HOME/archived_sessions`，默认本地根目录为 `~/.codex`。这些会话默认保留。见 [OpenAI 故障排查：Feedback and logs](https://developers.openai.com/codex/app/troubleshooting/)。

`~/Library/Application Support/Codex`、其中的 `Crashpad/pending` 与 `Library/Caches` 的 Codex 名称是待核对候选，并非所有版本必然存在的位置。只在真实目录记录命中后生成占用发现。继承的自定义 `CODEX_HOME` 同样只提供候选，绝不是隐式授权；其会话、配置和用途不明数据保持保护。日志数据库包括 `logs_*.sqlite` 及 WAL/SHM 文件时，说明需要整体考虑，不能运行期间单独删除日志数据库或其侧文件；不读取数据库内容。

签名或构建副本仅在系统临时目录的真实名称含 `codex`、`codesign` 或 `code-sign` 时提示黄色。明确写出“归属待确认”，不因名称便认定由 Codex 创建。项目目录必须由用户指定，不把所有 Codex 数据归为垃圾。

## 影视后期

Blackmagic 的官方编辑指南展示了每个工程可以指定 **Proxy generation location** 和 **Cache files location**，示例中两者不是同一个固定目录。因此不按一个写死的路径寻找所有渲染或代理文件。见 [DaVinci Resolve 17 官方编辑指南](https://documents.blackmagicdesign.com/UserManuals/DaVinci-Resolve-17-Editors-Guide.pdf)。

仅识别实际扫描到的 `CacheClip`、`ProxyMedia`、`OptimizedMedia`、`RenderCache` 等名称，以及真实存在的 DaVinci Resolve、JianyingPro、CapCut 应用路径中的 cache/log/temp 子目录。全部为黄色，说明必须在剪辑软件工程设置中核对真实位置、原始素材可用性与再生成条件。名称可由用户自定义，不能据此证明工程关联或所有文件可再生成。

剪映与 CapCut 没有将一条路径视为所有版本通用。候选页给出常见名称线索，并在已授权的 `Application Support`、`Caches`、`Logs`、`Containers` 与 `Movies` 中浅层发现真实名称。不同软件版本、容器目录和用户自定义缓存目录需要用户授权其实际位置。首版不解析软件配置文件，用户可在应用内确认后选择该目录扫描。

`Resolve Disk Database`、`Resolve Projects`、工程数据库、草稿、`.gallery`、原始素材、媒体文件及作品输出默认红色。未知视频文件不因巨大、旧或最近修改而建议清理。代理和优化媒体仍可能支撑离线工作及交付，优先由原应用管理。

## 授权与发现

候选位置不是扫描结果，也不是授权。未授权位置的状态为 `notAuthorized`，不尝试列目录或读取文件。用户选定的扫描根目录由界面授权机制提供。

已覆盖位置以目录描述符相对的 `fstatat(..., AT_SYMLINK_NOFOLLOW)`（与 `lstat` 等效的不跟随链接元数据检查）核对，区分 `available`、`missing`、`denied`、`unavailable` 与 `symbolicLink`。入口用 `O_NOFOLLOW_ANY` 拒绝路径中任何链接；子目录逐个 `openat` 并比对设备与 inode，避免路径替换导致越过授权范围。浅层发现同样不跟随链接。最多读取每个入口的 512 个目录项；Blackmagic 子入口只再查一层、最多 64 项，避免隐式全盘枚举。数量达到限制时属于有界名称发现，不代表全目录扫描。

发现不解析媒体或配置内容，也不自动遍历推荐位置。若无授权、读权限不足或候选位置没有命中，应选取软件实际配置的目录；界面不能编造路径的容量。

## 两次扫描的增长比较

第一阶段支持用户主动复查后的目录增长比较。第二阶段的每分钟后台采样与十分钟异常事件尚不在这一规则模块中。

只有两次扫描均正常完成、规范化后的授权根目录集合完全相同，且上一次扫描结束不晚于本次开始，才比较。目录必须在两次均存在、标识一致、且各自完整扫描；第一次读取的新授权目录、无权限恢复的目录与部分扫描目录不会被报告为增长。

其他位置存在未扫描部分时，仍可比较满足以上条件的完整子树。结果优先已识别用途的目录，再按正增长量选择最多 20 个互不包含的路径。这是用于追查的候选列表，可能不是所有增长的合计；不将父子增量相加。逻辑大小与分配大小的增量分开展示。

扫描不是文件系统事务快照，期间文件可变化。目录变大只能支持“在这个范围观察到增长”，无法单独证明某个应用导致整盘剩余容量减少。Swap、APFS 快照、授权范围外目录等仍可能影响容量；解释始终明确“原因待确认”。
